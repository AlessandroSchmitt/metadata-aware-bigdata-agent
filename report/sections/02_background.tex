\section{Background and Project Requirements}
\label{sec:background}


\subsection{Text-to-SQL over Structured Data}

Text-to-SQL addresses the problem of translating a natural-language
question into an executable SQL query over structured data. The task
requires more than natural-language understanding: a system must also
identify the relevant database objects, map expressions in the user
question to physical schema elements, infer the required joins and
conditions, and generate syntactically and semantically valid SQL.

Cross-domain benchmarks such as Spider have highlighted the difficulty
of generalizing Text-to-SQL systems to previously unseen schemas and
queries \cite{yu2018spider}. This distinction is particularly relevant
for data-lake analytics. In a heterogeneous environment, the user may
not know which physical source contains a requested concept, while the
same analytical concept can be represented differently across datasets.

Schema grounding is therefore a central part of the problem considered
in this project. The generated query must refer to the correct Spark SQL
tables and columns, but the user question is expressed using domain
language rather than physical identifiers. Cross-source questions add
another layer of complexity because the system must also identify the
relationships required to combine independently designed datasets.


\subsection{Retrieval-Augmented Generation and Metadata Grounding}

Retrieval-Augmented Generation (RAG) combines a generative model with
information retrieved from an external non-parametric source
\cite{lewis2020rag}. Instead of requiring the language model to rely only
on knowledge encoded in its parameters, relevant external information
can be selected at query time and included in the generation context.

The principle is useful for structured analytics, although the object
retrieved in this project differs from conventional document-oriented
RAG. The system does not retrieve arbitrary text passages as the final
evidence used to answer the question. Instead, it retrieves
\emph{metadata}: dataset descriptions, physical columns, semantic
concepts, aliases, relationships, and semantic rules. This metadata
acts as an intermediate grounding layer that helps the model construct
an executable query over the underlying data.

This distinction is important because semantic similarity alone is not
sufficient for multi-source query generation. A semantically relevant
column can imply a required join whose endpoint columns are not
independently similar to the natural-language question. For this reason,
the proposed system augments dense retrieval with deterministic
relationship expansion. Retrieval identifies candidate metadata,
whereas the catalog relationships provide structural information needed
to construct the final SQL context.


\subsection{Table-Augmented Generation for Data Analytics}

Recent work on Table-Augmented Generation (TAG) studies a broader
interaction between language models and structured databases
\cite{biswal2024tag}. TAG combines language-model reasoning with
operations executed by a data-management system, allowing natural
language interaction to exploit both model capabilities and structured
query processing.

The present project is narrower than the complete TAG formulation
because its main target is Text-to-Spark-SQL generation. Nevertheless,
it follows the same data-centric principle: the language model is not
treated as an autonomous source of analytical facts. Instead, it is
grounded on metadata describing structured sources, produces an
executable query, and delegates the actual computation to the data
processing engine.

This separation is especially useful for analytical questions involving
aggregation, filtering, grouping, and joins. Such operations can be
expressed explicitly in SQL and executed deterministically over the
curated datasets, while the language model is primarily responsible for
mapping the natural-language intent to the appropriate structured
operation.


\subsection{Spark SQL as the Execution Layer}

Apache Spark provides a distributed processing environment for
large-scale data analytics. Spark SQL extends Spark with structured
relational processing and integrates SQL queries with the Spark
execution engine \cite{armbrust2015sparksql}.

In this project, Spark SQL represents the execution boundary between
language-model generation and data computation. The LLM produces SQL,
but it does not calculate the analytical result itself. After
validation, Spark resolves the physical schema, plans the query, reads
the required Parquet datasets, performs joins and aggregations, and
returns the computed result.

This design has two advantages. First, query execution remains grounded
on the actual data rather than on values generated by the language
model. Second, the data-processing component can be evaluated
independently from the metadata and LLM components. The experimental
methodology therefore distinguishes \emph{catalog scale}, which concerns
the amount of metadata available to the retrieval system, from
\emph{data volume}, which concerns the number of physical records
processed by Spark.


\subsection{Big Data Dimensions and Project Requirements}

The course project specification asks students to identify a Big Data
problem, select data and methods, implement a working prototype, and
perform a non-trivial experimental evaluation
\cite{bigdataProject2026}. It also requires the project to address
\emph{Volume} together with at least one additional Big Data
``V''.

This project focuses on two dimensions: \emph{Volume} and
\emph{Variety}. Volume is represented by the taxi-trip data processed
by Spark. The curated Yellow Taxi source alone contains almost three
million records for the selected month, and the data-volume experiment
evaluates execution at progressively larger row counts.

Variety is represented by the integration of heterogeneous data
sources. Yellow Taxi, Green Taxi, Taxi Zones, and hourly weather
observations have different schemas, semantics, temporal
characteristics, and analytical roles. Cross-source requests therefore
require explicit metadata describing how physical fields and
granularities relate to each other.

The system is also aligned with the data-centric generative-AI focus of
the project specification \cite{bigdataProject2026}. Rather than
fine-tuning a model or increasing model complexity, the central design
question is how the representation, retrieval, and validation of data
metadata affect downstream query generation.


\subsection{Positioning of the Proposed System}

The resulting architecture can be viewed as a combination of three
ideas. From Text-to-SQL, it adopts natural-language-to-query
translation and executable result evaluation. From retrieval-augmented
generation, it adopts dynamic context selection. From data-management
systems, it uses an explicit catalog and Spark SQL as the authoritative
execution layer.

The main difference from a complete-catalog Text-to-SQL baseline is
therefore not the language model or the physical data. Both
configurations use the same model and query the same curated sources.
The experimental variable is the way in which metadata is selected and
presented before SQL generation.

This separation makes it possible to evaluate whether relation-aware
metadata selection can improve query generation while reducing prompt
size, and also to identify the conditions under which aggressive
metadata filtering loses information required for correct cross-source
queries.
